# ADR-0008: No server-side content processing

## Context
Fluxer's server reads content in several places: search indexing, unfurl, banned-phrase moderation, ClamAV and NSFW scanning, mention extraction and push previews. None of these can survive E2EE.

## Decision

| Feature | OSACA |
| --- | --- |
| Message search | **Client-side**, using a local encrypted index of what the Device has downloaded. Server-side search only for the [[GLOSSARY#Community Directory\|Community Directory]]. |
| Link previews | Generated by the **sender's client** and attached encrypted. **Off by default**, optionally through a proxy or Tor. Server unfurl is removed. |
| Moderation | By **Community Moderators**, who are Members and see content. **Reports** reach the Operator with the decrypted message; [[GLOSSARY#Message Franking\|Message Franking]] arrives in F4. No server-side scanning. |
| Push | **[[GLOSSARY#Wake-up Push\|Wake-up Push]]** only, with no content and no sender. Desktop relies on the WebSocket; web uses Web Push directly, with no relay. |
| Attachments | **Encrypted on the client** with a per-file key carried inside the encrypted message. S3 stores opaque blobs. Thumbnails and thumbhash are made on the client. The media proxy loses transforms and the external proxy. Public Community avatars and banners may stay plaintext. |
| Edits, reactions, deletes | **Encrypted MLS application messages.** A delete sends an encrypted tombstone and the server drops the ciphertext. `has_reaction`, `recent_mentions` and `saved_messages` leave the server; saved messages are kept locally. |
| Mentions | Computed **on the client**. The server wakes every Member, and each client decides whether to notify. |

## Consequences
> [!warning] Operator legal exposure
> Operators cannot inspect content. The operator docs must say this clearly, as Signal, Matrix and SimpleX do.

- Search only covers history that the Device has.
- Waking every Member costs more push traffic in large Communities.
